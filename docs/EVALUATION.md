# Evaluation & Empirical Verification

**Author:** Jagadeesh  
**Audit Run:** Seed `7`, 1,000 synthetic calls (`eval/results/latest.json`)  
**Determinism:** Fixed base epoch `1729000000.0`, seeded RNG, zero wall-clock dependencies, zero LLM calls.

---

## 1. Methodology

The evaluation benchmarks the **Atoms Call Ledger** against a **Naive Baseline** over an automated, seeded synthetic fault suite designed directly from the Smallest.ai Atoms webhook documentation.

- **Naive Baseline (`eval/baseline.py`)**: Represents a common first-pass integration. It parses JSON, appends events to a flat list without signature checking, performs no deduplication, lacks schema normalization, and acknowledges all requests with HTTP 200.
- **Atoms Call Ledger (`src/atoms_ledger/`)**: Implements raw-byte HMAC verification, persist-before-ack delivery logging, first-write-wins deduplication, authenticated quarantine, schema normalization, and ZDR deadline reconciliation.

## 4. Analysis: What These Numbers Do and Do Not Show

### What They Prove
1. **Cryptographic Integrity (M3 & M10)**: The ledger rejects 100% of tampered payloads and preserves authentic deliveries byte-for-byte without corruption.
2. **Order Independence (M11)**: Whether `analytics-completed` arrives before `post-conversation` or `pre-conversation`, the ledger converges on the identical canonical call record in 100% of permutations.
3. **Loss Prevention under ZDR (M6 & M7)**: Malformed authentic payloads are never dropped (100% quarantined), and 85.8% of injected loss scenarios are surfaced while the full 24-hour retention window remains available for backfill.

### What They Do NOT Prove
1. **Real Production Traffic**: Fault distributions were synthesized from public documentation; they were not sampled from live Smallest.ai production clusters.
2. **Universal Baseline**: The naive baseline is an illustrative reference constructed for this study; it does not represent any specific customer's proprietary codebase.
3. **Throughput at Scale**: Tests were performed in-memory and on local SQLite; they do not measure multi-region throughput under 10,000 requests/sec.

---

## 5. Threats to Validity

1. **Synthetic Fault Distributions**: Faults are artificially injected based on edge cases cited in documentation. Real telephony network loss patterns may exhibit temporal clustering or packet bursting not captured in a uniform distribution.
2. **Retention Anchor Approximation**: The ledger calculates deadline countdown using $\min(\text{timestamps})$ because Atoms docs state *"never later than your retention window"* without specifying whether the anchor is call start, call termination, or recording upload.
3. **Assumed Analytics Dispatch**: The ledger assumes calls terminating in `no-answer` do not expect `analytics-completed`. If Smallest.ai actually emits analytics for unanswered calls, M7 and M8 metrics will shift.

---

## 6. What Would Invalidate This Project

1. If Smallest.ai introduces **automatic webhook redelivery with exponential backoff and dead-letter queues**, client-side reconciliation would no longer be strictly necessary for durability.
2. If Atoms modifies its signature scheme to include a **mandatory timestamp header** (`X-Signature-Timestamp`), application-layer idempotency would no longer be the sole defense against replay attacks.
3. If Zero Data Retention is modified to **retain transcripts indefinitely** on failed webhook delivery, the urgency of pre-deadline API backfill would be eliminated.
